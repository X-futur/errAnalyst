# 记忆系统：短期进程内滚动摘要与长期用户记忆档案

Status: accepted

ErrAnalyst 需要让分析、修复建议和对话贴合用户习惯，而现有对话会话仅存进程内历史（ADR-0002 约定不落盘）且截断即丢信息。我们加入两层记忆：短期记忆保持进程内并新增惰性滚动摘要（真正发生截断时由 LLM 压缩被丢弃消息，不落盘、不推翻 ADR-0002）；长期记忆在 `~/.errAnalyst/memory.json`（格式 `memory-v1`）按用户全局保存修复偏好、修复建议偏好、错误分析偏好与常犯错误统计。长期记忆只存语义记忆（去情境化的偏好陈述）与统计记忆（按 errorType 聚合的报错频率），不存情景记忆——接受/拒绝等行为事件仅用于累加观察计数，事件本身不落盘；具体错误实例的"情景记忆"是 v2 演进方向。偏好来源混合：修复偏好从修复会话的接受/拒绝行为隐式学习（同一修改原因被接受 ≥2 次才自动写入，仅 1 次时作为待确认候选，拒绝不产生条目）；修复建议偏好与错误分析偏好以显式声明为主，隐式仅作低置信提示；常犯错误按 errorType 自动计数，独立于会淘汰的 200 条错误缓存。记忆加载采用按产出类别路由的全量注入（偏好上限 30 条，常犯错误取 Top 5），不做 RAG 语义检索——条目量小，路由已承担"按需"筛选，语义召回对短偏好句无增益且引入 embedding 依赖。记忆按产出类别注入分析、修复补丁与对话三类 prompt 的 "## 用户记忆" 块（每条标注来源与置信度，行为推断标注仅供参考），由 `erranalyst memory config` 命令交互式维护（并注册 VS Code 同名命令 `errAnalyst.memoryConfig`，availability: both，沿用 `provider set` 的交互模式），受 `errAnalyst.memory.enabled` 总开关控制。

Considered Options:
- 短期记忆落盘、跨重启恢复（被否：报错视图本就一次性，违背 ADR-0002，收益低）
- 偏好全显式或全隐式（被否：全显式负担大且用户说不清，全隐式误学习风险高）
- 记忆按工作区分隔（被否：偏好是用户级属性，v1 保持单一全局档案；如出现跨项目冲突再演进覆盖层）
- 独立 webview 管理视图（被否：用户要求管理走 CLI；单命令交互式与现有 `provider set` 模式一致，共享同一 memory-store 模块）
- VS Code globalState 存储（被否：内容不可见、不可手工编辑/备份，偏离现有本地 JSON 文件模式）
- 记忆无差别注入所有 prompt（被否：分析时读到修复偏好是噪音，按产出路由更聚焦且省 token）
- RAG 语义检索按需加载（被否：v1 条目量小且已按类别路由，RAG 引入 embedding 依赖无增益；如 v2 加入情景记忆再演进）

Consequences:
- ADR-0002 的"对话历史不落盘"保持有效，短期记忆在其上增加摘要层。
- "本地缓存"（错误分析缓存，不参与自动分析）与"长期记忆"（参与自动分析）是两套独立持久化，语义不可混用。
- 隐式学习依赖修复会话的"修改原因"文本，判重需要归一化比较（如 "None 保护" 与 "添加 None 检查" 视为同一条）。
- 记忆注入会增加每次调用 token，偏好条目需设数量上限、常犯错误取 Top N。
