# 0013 流式运行时错误检测

此前错误分析只在命令结束（非零退出）与启动后一次性检查时触发，长驻 Python 服务运行期间打印的 Traceback 或 ERROR 级日志永远不会被分析。我们决定引入流式特征触发：持续消费终端输出（`onDidWriteTerminalData` 提案 API 可用时为主，`TerminalLinkProvider` 行回调为稳定兜底），命中报错特征后等待输出稳定（1.2 秒空闲、至多 5 秒）再解析，并按识别档位分级处理。

具体决策：

- **分档门槛与冷却**：结构化档（Traceback 或可解析出具体 Python 错误类型）10 秒同签名去重；日志档（ERROR/CRITICAL/FATAL 行、无栈帧）60 秒同内容去重。冷却期内只累计"常犯错误"次数，不重复调用 AI。
- **语义区分**：结果新增触发来源（运行时报错 / 命令结束报错）与识别档位（结构化 / 日志行），修正 `hasExitCode`——运行时报错不再误标为非零退出；视图展示来源标记，分析 prompt 告知"服务仍在运行"。
- **焦点策略**：命令结束报错维持自动展开；运行时报错只更新视图内容并以未读角标提示，不抢焦点。
- **崩溃合并**：服务崩溃时流式触发与命令结束触发可能先后命中同一报错——命令结束事件到达时取消未触发的流式等待；若流式分析已触发，则在 10 秒内把同一错误升级为命令结束报错（补退出码、改来源、更新视图），不重复调用 AI。
- **观察范围**：全部终端，维持只解析 Python 报错；不因日志档放宽到其他语言。

Status: accepted

## Considered Options

- **周期轮询**：每隔数秒全量解析缓冲区。实现简单，但延迟高、重复分析、噪音大。
- **仅崩溃捕获**：只处理 exit code ≠ 0。无法覆盖"服务还活着但已报错"的核心场景。
- **不区分来源统一处理**：运行时报错与命令结束报错同权展示分析。会让长驻服务场景反复打断并丢失退出码语义。

## Consequences

- 长驻服务输出频繁时会先缓冲、等 1.2 秒空闲（至多 5 秒）才分析，报错反馈有短暂延迟。
- `onDidWriteTerminalData` 是提案 API，发布版扩展不可用；稳定兜底依赖 `TerminalLinkProvider` 的逐行回调，该通道只覆盖行级输出，未开启 Shell Integration 且无提案 API 时流式捕获可能不完整。
- 日志档分析无栈帧与文件定位，AI 分析质量依赖上下文捕获，可能给出低置信结论。
