# 关键决策：记忆系统

### 决策 1：两层记忆架构（短期进程内 + 长期 memory.json）

- **背景**：对话会话只有进程内历史且截断即丢，需要贴合用户习惯的记忆。
- **选项**：短期落盘跨重启恢复 / 跨报错延续 / 进程内 + 滚动摘要；长期存 VS Code globalState / 本地 JSON。
- **选择与理由**：短期保持不落盘并新增惰性滚动摘要（截断时才由 LLM 压缩）；长期用 `~/.errAnalyst/memory.json`（`memory-v1`，用户全局）。理由：报错视图一次性、落盘收益低；JSON 可见可备份且延续 err-store 模式。
- **代价**：会话摘要随会话结束丢失；memory.json 需自管版本迁移。
- **后续影响**：ADR-0002"对话历史不落盘"保持有效；短期与长期的分界（摘要落盘即滑向长期）是未来演进红线。

### 决策 2：长期记忆内容模型与来源（语义 + 统计，非情景）

- **背景**：用户提出修复偏好、修复建议偏好、错误分析偏好、常犯错误四类。
- **选项**：四类分开 / 合并修复两类 / 全显式 / 全隐式。
- **选择与理由**：四类分开并对应现有术语（修复建议=纯文字、修复补丁=代码）；来源混合——修复偏好从接受/拒绝行为隐式学习（同一修改原因 ≥2 次转 active、1 次为候选、拒绝不产生条目），建议/分析偏好以显式声明为主，常犯错误自动按 errorType 计数。只存语义偏好与统计，不存可回溯事件（非情景记忆）。
- **代价**：隐式学习有误学风险；候选机制引入管理成本。
- **后续影响**：情景记忆 + RAG 是 v2 演进方向；归一化判重的语义边界需谨慎（"检查/保护"强行合并有污染风险）。

### 决策 3：加载方式——按类别路由全量注入，不做 RAG

- **背景**：长期记忆如何进入提示词。
- **选项**：RAG 语义检索 / 无差别全量注入 / 按产出类别路由全量注入（上限 30 条 + errorStats Top 5）。
- **选择与理由**：v1 条目量小、路由已承担"按需"筛选，RAG 引入 embedding 依赖无增益；按分析/修复补丁/对话三类 prompt 路由，行为推断条目标注"仅供参考"。
- **代价**：条目超限时按 lastUsedAt 截断可能丢偏好；每次注入会 touch lastUsedAt 并落盘。
- **后续影响**：条目量膨胀或引入情景记忆时再评估 RAG；该被否方案已写入 ADR-0010。

### 决策 4：管理入口用 CLI 命令 `erranalyst memory config`

- **背景**：长期记忆需要查看、增删改、候选确认、总开关。
- **选项**：独立 webview 管理视图 / CLI 单命令交互式（+ VS Code 同名命令）。
- **选择与理由**：用户明确要求 CLI；单命令交互式沿用 `provider set` 的 readline 模式，与扩展共享 memory-store，不复制读写逻辑。
- **代价**：纯终端交互在 Windows（settings.json 路径问题）与无终端场景受限。
- **后续影响**：VS Code 侧注册 `errAnalyst.memoryConfig`（availability both）；Windows 适配需按平台解析 settings 路径。

### 决策 5：VSIX 打包必须放行 CLI 依赖的 shared 模块

- **背景**：`.vscodeignore` 排除 `src/**`，导致 `memory-store.js` 漏进 VSIX，CLI 在安装包内缺模块。
- **选项**：仅白名单 err-store（旧） / 白名单全部 CLI 依赖（err-store + memory-store 的 .js/.d.ts）。
- **选择与理由**：CLI 运行时 `require('../src/shared/...')`，必须随包分发；打包后 unzip 验证作为发布检查项。
- **代价**：VSIX 内多几个源码文件（可接受）。
- **后续影响**：以后新增 CLI 依赖的 shared 模块，必须同步更新 `.vscodeignore` 白名单。
